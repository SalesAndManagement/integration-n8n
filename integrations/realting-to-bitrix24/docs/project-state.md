## Що з'ясовано про API Realting (перевірено запитами)

- Експорт: `GET https://realting.com/api/orders/export`, ключ у заголовку **`X-Api-Key`**
  (не Bearer). Сторінка кабінету `realting.com/ru/account/orders/api-export` закрита логіном,
  публічної документації немає.
- Відповідь: `{"success": true, "meta": {page, limit, total, pages}, "data": [...]}`.
  `success: false` може приходити з кодом 200 — обробляється окремо.
- **Параметри дат ігноруються**: ендпоінт щоразу віддає весь архів (на момент налаштування
  89 заявок). Тому вікно застосовується на нашому боці, а в проді `SYNC_WHOLE_ARCHIVE=true` —
  бар'єром служить дедуплікація за `id`, не дата.
- **Контакти маскуються**: заявки зі `status_id: 1` («Request not accepted to work») приходять
  із затертими полями — `"Гал***"`, `"+488******68"`, `"gal***@varemestate.com"`. Відкриваються
  лише після прийняття заявки в роботу в кабінеті. **Те саме стосується хуків** — платформа
  шле заявку одразу, але з закритими контактами.
- Структура заявки: `id`, `status_id`, `status_title`, `name`, `phone`, `email`, `message`,
  `region`, `lang_code`, `lang_title`, вкладені `object{id,title,type_title,url,price}` і
  `utm{source,medium,campaign}`, `created_at`, `received_at`.
- Хуки приходять з IP `167.235.183.200`.

## Що з'ясовано про Bitrix24

- Портал `varem-estate.bitrix24.eu`, вхідний вебхук від користувача 5714, права CRM.
- Поле зовнішнього ID: **`UF_CRM_1789452928715`** (портал згенерував власний код замість
  очікуваного `UF_CRM_REALTING_ID`).
- **Емодзі ламають поля**: символ поза BMP (напр. `🔒`, U+1F512) у `TITLE` призводить до того,
  що портал зберігає **порожній заголовок**, не повертаючи помилки. У текстах лідів емодзі
  не використовуються; є тест, який це стереже.
- Ліміт REST ~2 запити/сек — клієнт тротлить і повторює `QUERY_LIMIT_EXCEEDED`.
- Тексти для менеджерів — **російською** (заголовок і коментар ліда).

## Ключові рішення

**Режим `IMPORT_MASKED=true`.** Лід створюється одразу в момент звернення — з позначкою
«(контакты скрыты)» в заголовку, без полів телефону й пошти, з підказкою прийняти заявку в
кабінеті Realting. Коли контакти відкриваються, сервіс підставляє їх **у той самий лід**
(`crm.lead.update`), без дубля. Працює навіть при втраті бази стану: портал питають про
`HAS_PHONE`/`HAS_EMAIL` наявного ліда.

**Старт «тільки нові».** `realting-sync seed` позначив історію: 51 заявку з відкритими
контактами як `baseline` (позаду назавжди), 38 замаскованих як `masked` (приїдуть, коли
контакти відкриються). У CRM при цьому нічого не створено.

**Два канали.** Хуки (миттєво) + опитування експорту кожні 5 хв (страховка, якщо хук не дійде).
Дедуплікація спільна — подвійних лідів не буде.

**Черга.** Приймач відповідає `200` одразу після запису в SQLite, доставкою займається воркер.
Помилка Bitrix24 → повтор за схемою 1 хв → 5 хв → 15 хв → 1 год → 6 год, потім `failed`
(повертається в чергу через `drain --retry-failed`). Заявка не губиться.

## Команди

```bash
realting-sync check      # конфіг + доступ до обох систем
realting-sync probe      # сира відповідь Realting + зріз за статусами
realting-sync sync       # опитування експорту (--dry-run, --since, --all, --force)
realting-sync serve      # приймач хуків (під systemd)
realting-sync drain      # доставити чергу (--retry-failed)
realting-sync seed       # позначити наявні заявки, нічого не створюючи
realting-sync stats      # стан бази й черги

sudo ./deploy/diagnose.sh 12    # діагностика всього ланцюга за 12 годин
```

Логи: `sudo journalctl -u realting-webhook -f`, `sudo journalctl -u realting-sync -n 30`.
Оновлення: `cd /opt/src && sudo git pull origin claude/adoring-cori-cmo1iz &&
cd integrations/realting-to-bitrix24 && sudo ./deploy/install.sh`.

## Баги, знайдені на бойових даних (не повторювати)

1. **Емодзі в `TITLE`** → порожній заголовок ліда без помилки від API.
2. **`store_true` перекривав конфіг**: `--all` за замовчуванням дає `False`, і цей `False`
   затирав `SYNC_WHOLE_ARCHIVE=true`. Прапорці тепер лише вмикають режим.
3. **Порожня сторінка пагінації** `{"data": []}` трактувалась як одна «заявка».
4. **Замаскований e-mail формально валідний** (`n***@gmail.com`) — без окремої перевірки
   потрапляв би в поле контакту.
5. **Кирилиця в токені** (скопійований плейсхолдер) давала нечитабельний `UnicodeEncodeError`
   з надр `http.client` — тепер валідується при завантаженні конфігу.

## Відкриті питання

- **Чи може Realting слати в хуку відкриті контакти?** Питання поставлене клієнту, відповіді
  ще немає. Якщо так — проміжний крок із «(контакты скрыты)» стане непотрібним.
- **Дозаповнення контактів не перевірене на живій заявці.** Потрібно прийняти заявку 164070
  або 164071 в роботу на Realting і переконатись, що телефон підставився в лід
  (`journalctl -u realting-sync | grep дозаповн`).

## Гігієна, яку варто закрити

- **SSH-ключ не налаштований**, вхід досі по паролю (`sudo sshd -T | grep passwordauth` → `yes`).
  Команди `ssh-keygen` / `ssh-copy-id` виконувати **на маку**, не на сервері.
- **Токен Bitrix-вебхука засвітився в переписці** — варто перевипустити: новий вхідний вебхук
  у порталі → підмінити `BITRIX_WEBHOOK_URL` → `systemctl restart realting-webhook` →
  видалити старий.
- Сервер просить рестарт (`*** System restart required ***`), оновлення Ubuntu 24.04 доступне.
- На сервері встановлений Cloudflare WARP у режимі проксі (порт 40000) — інтеграції не заважає.

```bash

PYTHONPATH=src:tests python3 -m unittest discover -s tests -t tests
```

193 тести, Python 3.10+, лише стандартна бібліотека (ні venv, ні pip). Юніт-тести не ходять
у мережу; наскрізні піднімають локальний HTTP-сервер і ганяють справжній CLI, включно з повним
шляхом хука (POST → черга → `drain` → Bitrix24). Окремий набір — на реальному зразку відповіді
`/api/orders/export`.
