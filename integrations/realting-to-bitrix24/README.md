# Realting.com → Bitrix24: імпорт заявок через n8n

Готовий каркас інтеграції: власний сервер з n8n, поллінг експорту заявок з realting.com,
нормалізація, трирівнева дедуплікація та створення лідів у Bitrix24.

---

## 1. Аналіз: що вдалося встановити

**Сторінка `https://realting.com/ru/account/orders/api-export` закрита авторизацією.**
Перевірено: запит без сесії віддає `302 → https://realting.com/ru/user/login`. Публічної
документації API Realting у відкритому доступі немає (ні в `robots.txt`, ні в довідці порталу,
ні в пошуку). Тобто **специфікацію можна зняти тільки з вашого кабінету** — це перший крок,
без нього будь-який код буде здогадкою.

Через це інтеграція побудована так, щоб невідомий формат не блокував роботу:
парсер приймає і «голий» масив, і будь-яку обгортку (`data` / `items` / `orders` / `result` /
`rows`), а поля шукає за списком вірогідних назв (`id|order_id|uuid`, `phone|contact_phone`,
`message|comment|text` тощо). Коли ви пришлете реальну відповідь — правки зведуться до
уточнення 2-3 рядків у ноді `Нормалізувати заявки` і назв query-параметрів дат.

### Що потрібно зняти з кабінету (5 хвилин)

1. **URL експорту** з тієї сторінки (повний, з query-параметрами, якщо вони є).
2. **Спосіб авторизації**: токен у заголовку `Authorization: Bearer`, окремий заголовок
   (`X-Api-Key`) чи параметр в URL (`?token=`).
3. **Приклад відповіді** — 1-2 реальні заявки (JSON або XML; персональні дані можна замалювати,
   важлива структура й назви полів).
4. **Формат/фільтри**: чи є параметри `date_from` / `updated_since` / пагінація, чи є ліміт
   на частоту запитів.
5. Чи вміє платформа **сама слати вебхук** при новій заявці — тоді поллінг зайвий (див. п.3).

## 2. Архітектура

```
realting.com (api-export)
        │  HTTPS GET, кожні 5 хв, вікно [останній запуск − 15 хв ; зараз]
        ▼
   ┌──────────────────────────────────────────────┐
   │  VPS (Ubuntu 24.04)                          │
   │  Caddy (Let's Encrypt) → n8n → PostgreSQL    │
   └──────────────────────────────────────────────┘
        │  нормалізація → дедуп (3 рівні) → REST
        ▼
   Bitrix24: crm.lead.add / crm.timeline.comment.add
```

**Чому поллінг, а не вебхук за замовчуванням:** сторінка називається «API export», тобто
платформа найімовірніше віддає вибірку на запит, а не пушить події. Якщо push все ж є —
у комплекті лежить готовий webhook-воркфлоу, і поллінг просто вимикається.

**Чому окремий сервер, а не n8n Cloud:** заявки з персональними даними, потрібен контроль
над логами й ретенцією, плюс на цьому ж інстансі потім живуть інші інтеграції. n8n Cloud
(≈ €24/міс) теж робочий варіант, але дорожчий і без доступу до контейнера.

### Вартість і ресурси

| Позиція | Рекомендація | Ціна |
|---------|--------------|------|
| VPS | Hetzner CX22 / Contabo VPS S — 2 vCPU, 4 GB RAM, 40 GB SSD | ≈ €5–8/міс |
| Домен | `n8n.вашдомен.com` (A-запис на IP) | вже є |
| TLS | Let's Encrypt через Caddy | 0 |
| n8n | Community, self-hosted | 0 |
| **Разом** | | **≈ €5–8/міс** |

4 GB RAM — з запасом: n8n + Postgres на такому потоці заявок їдять < 1 GB. 2 GB теж вистачить,
але при наступних воркфлоу (AI-ноди, парсинг) впреться.

## 3. Склад репозиторію

```
integrations/realting-to-bitrix24/
├── .env.example                          # усі секрети — тільки тут, у JSON їх немає
├── deploy/
│   ├── install.sh                        # Docker + ufw + fail2ban на чистій Ubuntu
│   ├── docker-compose.yml                # Caddy + n8n + PostgreSQL
│   ├── Caddyfile                         # HTTPS-термінація
│   └── backup.sh                         # щоденний pg_dump, ретенція 14 днів
├── workflows/
│   ├── realting_orders_to_bitrix24.json  # ОСНОВНИЙ: поллінг → дедуп → лід
│   ├── realting_webhook_to_bitrix24.json # запасний: приймання push від Realting
│   └── realting_sync_error_alert.json    # алерт у Telegram при падінні
└── docs/
    ├── field-mapping.md                  # таблиця мапінгу полів + логіка дедупу
    └── bitrix24-setup.md                 # вебхук, UF-поле, джерело, ліміти REST
```

### Логіка основного воркфлоу

`Schedule (5 хв)` → `Конфіг` (секрети з `$env`) → `Вікно синхронізації` (від останнього успішного
запуску мінус 15 хв нахлесту; стан у static data) → `HTTP GET Realting` (3 ретраї) →
`Нормалізувати заявки` (розгортання обгортки, мапінг, відсів без контактів) →
`crm.lead.list` по `UF_CRM_REALTING_ID` → якщо є — стоп → `crm.duplicate.findbycomm` по телефону →
якщо дубль — коментар у таймлайн існуючого ліда, якщо ні — `crm.lead.add` →
`Зафіксувати стан` (processedIds + lastSyncIso).

Ключові властивості:

- **ідемпотентність** — заявка не задублюється ні при нахлесті вікон, ні при ретраях,
  ні при перезапуску контейнера;
- **нічого не губиться** — вікно з нахлестом 15 хв покриває підвисання платформи; оригінальний
  обʼєкт заявки зберігається в `raw` і видно в логах виконання;
- **ліміт Bitrix24** (2 запити/сек) враховано батчингом на нодах створення лідів;
- **алерт** — окремий Error Workflow шле в Telegram назву ноди, текст помилки й лінк на виконання.

## 4. Розгортання

```bash
# 1. на свіжому VPS
git clone <цей репозиторій> /opt/n8n && cd /opt/n8n/integrations/realting-to-bitrix24
sudo ./deploy/install.sh

# 2. секрети
cp .env.example .env
openssl rand -hex 32           # → N8N_ENCRYPTION_KEY
openssl rand -base64 24        # → POSTGRES_PASSWORD
nano .env

# 3. підняти стек
docker compose --env-file .env -f deploy/docker-compose.yml up -d
docker compose --env-file .env -f deploy/docker-compose.yml logs -f n8n

# 4. відкрити https://<домен>, створити адмін-акаунт,
#    Workflows → Import from File → усі три файли з workflows/

# 5. бекапи
echo "0 3 * * * /opt/n8n/integrations/realting-to-bitrix24/deploy/backup.sh" | sudo crontab -
```

Перед активацією основного воркфлоу: **Execute Workflow вручну** з тимчасово збільшеним
`firstRunDays`, перевірити на 1-2 заявках, що лід у Bitrix24 створюється з правильними полями,
і лише потім вмикати розклад.

## 5. Безпека

- Секрети лише в `.env` на сервері (файл у `.gitignore`); у JSON воркфлоу — тільки `$env.*`.
- `N8N_ENCRYPTION_KEY` не можна міняти після першого запуску — інакше злетять усі креденшели.
- Порти назовні: 22 / 80 / 443. Postgres і n8n не публікуються, живуть у docker-мережі.
- Вебхук Bitrix24 — від імені технічного користувача з правами лише на CRM.
- Ретенція логів виконань — 14 днів (`EXECUTIONS_DATA_MAX_AGE=336`), бо в них персональні дані.
- Рекомендую ввімкнути 2FA на акаунті n8n і обмежити SSH ключами.

## 6. Наступні кроки

4. Далі за потреби: маршрутизація на менеджерів за мовою/регіоном заявки, автоматична
