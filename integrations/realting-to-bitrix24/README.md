# realting-sync — імпорт заявок realting.com у Bitrix24

Сервіс на чистому Python (стандартна бібліотека, без залежностей і venv): приймає хуки
realting.com про нові заявки, кладе їх у чергу й створює ліди в Bitrix24. Працює під systemd,
стан і черга — у SQLite.

```
realting.com                    VPS                                   Bitrix24
 ┌──────────┐   POST    ┌──────────────────────────────┐        ┌──────────────────┐
 │ нова     │ ────────► │ Caddy :443 (TLS)             │        │ crm.lead.add     │
 │ заявка   │           │   └─► приймач :8080 → черга  │ ─────► │ crm.duplicate.*  │
 └──────────┘  200 OK   │       воркер: черга → CRM    │        │ crm.timeline.*   │
                        └──────────────────────────────┘        └──────────────────┘
```

Приймач відповідає Realting `200` одразу після запису в чергу, а доставкою в Bitrix24
займається воркер. Тому недоступний портал, мережевий збій чи рестарт сервера не призводять
до втрати заявки: запис лишається в черзі й повторюється з наростаючою паузою (1 хв → 6 год).

## Два канали

| Канал | Команда | Коли потрібен |
|-------|---------|----------------|
| **Хуки** (основний) | `serve` + `drain` | Realting шле POST при кожній новій заявці |
| **Поллінг** (страховка) | `sync` | довибірка з `https://realting.com/api/orders/export` |

Обидва канали варто тримати ввімкненими: хук дає миттєву реакцію, поллінг підбирає заявки,
хук по яких не дійшов (мережа, рестарт, помилка на боці платформи). Дедуплікація спільна,
тому подвійного ліда не буде.

Про ендпоінт експорту відомо точно (перевірено запитом): ключ передається заголовком
`X-Api-Key`, відповідь — JSON у конверті `{"success": …}`; відмова з кодом 200 обробляється
окремо й не потрапляє в CRM як зіпсована заявка.

## Стан справ

Сторінка `https://realting.com/ru/account/orders/api-export` закрита авторизацією
(перевірено: `302 → /ru/user/login`), публічної специфікації немає. Тому сервіс написаний
так, щоб невідомий формат не блокував роботу:

- приймає JSON, XML і form-urlencoded (зокрема JSON у полі `payload`);
- розгортає будь-яку обгортку відповіді (`data` / `items` / `orders` / `result` / `rows` …);
- кожне поле шукає за списком вірогідних назв, включно з вкладеними (`client.phone`);
- назви параметрів запиту (дати, пагінація) і спосіб авторизації задаються в конфізі,
  а не в коді;
- ключ хука приймається чотирма способами (`?token=`, власний заголовок, `Bearer`,
  HMAC-підпис) — вибирається через `WEBHOOK_AUTH_MODE`;
- команда `probe` показує сиру відповідь і результат мапінгу — цим і знімається специфікація.

Що треба з кабінету: **ключ** (він іде у `WEBHOOK_TOKEN`) і **адреса**, яку туди вписати —
`https://<домен>/realting/webhook?token=<ключ>`. Перший же реальний хук покаже справжні назви
полів (`journalctl -u realting-webhook`), після чого мапінг — це правка конфігу, не коду.

## Встановлення

```bash
sudo apt update && sudo apt -y install git        # Python 3.10+ в Ubuntu 22.04 вже є
# -b обовʼязково: папка з сервісом живе на робочій гілці, не на main
sudo git clone -b claude/adoring-cori-cmo1iz https://github.com/SalesAndManagement/integration-n8n /opt/src
cd /opt/src/integrations/realting-to-bitrix24
sudo ./deploy/install.sh
```

Якщо репозиторій уже склонований (гілка `main`) — просто перемкніть її:

```bash
cd /opt/src && sudo git checkout claude/adoring-cori-cmo1iz
cd integrations/realting-to-bitrix24 && sudo ./deploy/install.sh
```

Інсталятор створює системного користувача `realting`, кладе код у `/opt/realting-sync`,
конфіг у `/etc/realting-sync.env` (права `640`), стан у `/var/lib/realting-sync`,
команду `/usr/local/bin/realting-sync` і юніти systemd.

## Налаштування і запуск

```bash
sudo nano /etc/realting-sync.env                    # WEBHOOK_TOKEN + BITRIX_WEBHOOK_URL
sudo -u realting realting-sync check                # конфіг і доступ до Bitrix24
sudo systemctl enable --now realting-webhook        # приймач на 127.0.0.1:8080
sudo ./deploy/install-caddy.sh webhook.example.com  # HTTPS назовні (Let's Encrypt)
sudo systemctl enable --now realting-sync.timer     # страховка: розбір черги кожні 5 хв
```

Адреса, яку вписати в кабінеті Realting:

```
https://<домен>/realting/webhook?token=<WEBHOOK_TOKEN>
```

Перевірка ззовні — має відповісти `{"status":"ok"}`:

```bash
curl -s https://<домен>/healthz
curl -s -X POST "https://<домен>/realting/webhook?token=<WEBHOOK_TOKEN>" \
  -H 'Content-Type: application/json' \
  -d '{"id":"test-1","name":"Тест","phone":"+380671234567","message":"перевірка"}'
sudo -u realting realting-sync stats                # заявка має зʼявитись у черзі
```

Перед першим запуском у Bitrix24 має бути створене поле ліда `UF_CRM_REALTING_ID` —
див. [`docs/bitrix24-setup.md`](docs/bitrix24-setup.md). `check` окремо про це попередить.

## Команди

| Команда | Що робить |
|---------|-----------|
| `realting-sync serve` | приймач хуків + фоновий воркер черги (основний режим) |
| `realting-sync drain` | вручну доставити в Bitrix24 те, що чекає в черзі |
| `realting-sync drain --retry-failed` | повернути в чергу записи, що вичерпали спроби |
| `realting-sync sync` | поллінг: забрати нові заявки з експорту і створити ліди |
| `realting-sync sync --dry-run` | показує, що створив би, нічого не пишучи |
| `realting-sync sync --since 2026-09-01` | разова довибірка за період (ігнорує збережений стан) |
| `realting-sync sync --all` | весь архів заявок без обмеження за датою (разовий перенос історії) |
| `realting-sync sync --force` | ігнорує локальну базу оброблених (дедуп у Bitrix24 лишається) |
| `realting-sync probe --days 30 --raw` | сира відповідь Realting + результат мапінгу |
| `realting-sync check` | перевірка конфігу, доступу до Realting і Bitrix24 |
| `realting-sync stats` | скільки заявок синхронізовано і до якого моменту |

Логи приймача: `journalctl -u realting-webhook -f`; розбір черги: `journalctl -u realting-sync -f`.

## Маскування контактів — головне обмеження платформи

Realting віддає заявки, не прийняті в роботу, із затертими контактами:

```json
{"id": 162275, "status_title": "Request not accepted to work",
 "name": "Ник***", "phone": "+790******21", "email": "n***@gmail.com"}
```

Такі заявки в CRM не потрапляють (`SKIP_MASKED=true`): дзвонити нікуди, а зайнятий
`UF_CRM_REALTING_ID` завадив би імпортувати ту саму заявку пізніше, коли контакти
відкриються. Скільки заявок замасковано — показує `realting-sync probe` у зрізі за статусами.
Якщо потрібно вантажити все підряд — `SKIP_MASKED=false`.

## Як це працює

**Приймання хука.** Перевірка ключа (constant-time, без витоку по таймінгу) → розбір тіла →
запис у чергу → `200 {"status":"accepted"}`. Чужий запит отримує `401` і в чергу не потрапляє,
зламане тіло — `400`. `GET` на адресу хука повертає `200` — деякі платформи так перевіряють URL
перед збереженням. Приймач слухає лише `127.0.0.1`, назовні його публікує Caddy з TLS.

**Черга.** Кожна доставка зберігається сирою. Воркер (усередині `serve`, кожні 5 с) бере
записи, мапить і несе в Bitrix24. Помилка порталу → пауза 1 хв, 5 хв, 15 хв, 1 год, 6 год,
після чого запис позначається `failed` і чекає `drain --retry-failed`. Таймер `realting-sync`
кожні 5 хвилин розбирає чергу незалежно від приймача — страховка на випадок його рестарту.

**Вікно вибірки (поллінг).** Експорт Realting не звужується параметрами дат — він щоразу
віддає весь архів, тому вікно застосовується на нашому боці, за `created_at` заявки.
Інакше перший же прогін завантажив би в CRM усю історію. Разовий перенос історії робиться
свідомо: `sync --all`. Від часу останнього успішного прогону мінус нахлест 15 хвилин
(`SYNC_OVERLAP_MINUTES`) до «зараз». Перший запуск бере останні 7 днів
(`SYNC_FIRST_RUN_DAYS`). Вікно зсувається **лише після повністю успішного прогону**:
якщо хоч одна заявка впала на помилці Bitrix24, наступний запуск спробує її ще раз.

**Дедуплікація, три рівні:**

1. SQLite `/var/lib/realting-sync/state.db` — заявка, вже імпортована цим сервісом, не піде вдруге
   (Realting може повторити доставку хука — це нормально й безпечно);
2. `crm.lead.list` за `UF_CRM_REALTING_ID` — захист після відновлення з бекапу чи `--force`;
3. `crm.duplicate.findbycomm` за телефоном (потім за поштою) — якщо контакт уже є в CRM,
   новий лід не створюється, а в таймлайн наявного падає коментар із текстом заявки.
   Вимикається через `BITRIX_COMMENT_ON_DUPLICATE=false`.

**Стійкість.** Мережеві збої та 5xx — 3 спроби з експоненційним бекофом. `QUERY_LIMIT_EXCEEDED`
від Bitrix24 — окремий ретрай із паузою; крім того, запити до порталу тротляться до
~2 на секунду (ліміт Bitrix24). Заявки без ID або без жодного контакту не імпортуються,
а потрапляють у лог із причиною.

**Мапінг.** Типові назви полів — у `src/realting_sync/normalize.py`. Якщо реальні назви інші,
не треба правити код: створіть `/etc/realting-sync.map.json` і вкажіть його в
`REALTING_FIELD_MAP_FILE`:

```json
{
  "external_id": ["zayavka_nomer"],
  "phone": ["kontakt.telefon"],
  "comment": ["tekst_soobscheniya"]
}
```

Повна таблиця полів — у [`docs/field-mapping.md`](docs/field-mapping.md), налаштування хука
в кабінеті Realting — у [`docs/webhook-setup.md`](docs/webhook-setup.md).

## Розробка

```bash
cd integrations/realting-to-bitrix24
PYTHONPATH=src:tests python3 -m unittest discover -s tests -t tests -v
```

169 тестів. Юніт-тести не ходять у мережу (транспорт і клієнти підмінені заглушками);
наскрізні піднімають справжній HTTP-сервер: один грає за обидві платформи, інший ганяє
повний шлях хука (POST → черга → `drain` → Bitrix24).
Окремий набір ганяє мапінг на реальному зразку відповіді `/api/orders/export`
(вкладені `object` та `utm`, `lang_code: null`, маскування, пагінація за `meta.pages`).
Покрито також: нормалізацію (JSON, XML, form-urlencoded, вкладені обʼєкти, сміттєві телефони),
перевірку ключа в усіх чотирьох режимах (включно з HMAC і підробленим тілом), коди
відповіді приймача, паралельні доставки, ретраї з наростаючою паузою, вичерпання спроб і
повернення в чергу, троттлінг Bitrix24, дедуплікацію, `--dry-run`, частковий збій, конфіг.

## Структура

```
src/realting_sync/
  config.py       конфіг зі змінних оточення + валідація
  httpclient.py   urllib + ретраї, розбір JSON/XML
  webhook.py      приймач хуків: перевірка ключа, розбір тіла, запис у чергу
  realting.py     клієнт експорту: авторизація, параметри, пагінація
  normalize.py    сира заявка → Lead (мапінг, чистка телефонів/пошти)
  bitrix.py       REST-клієнт Bitrix24: троттлінг, помилки, поля ліда
  state.py        SQLite: черга хуків, оброблені заявки, момент синхронізації
  sync.py         оркестрація: черга, вікно, дедуп, звіти
  cli.py          serve | drain | sync | probe | check | stats
deploy/           install.sh, install-caddy.sh, systemd-юніти, Caddyfile
docs/             мапінг полів, налаштування Bitrix24
```
