# Діагностика доступу до BAF: результат

Дата перевірки: 2026-09-17. Хост: `vladiyan.extranet.club:46795` (195.238.184.86).

## Що показали тести

| Тест | Результат |
|---|---|
| `nc -z vladiyan.extranet.club 46795` | порт відкритий |
| `curl http://...:46795/` | `Connection reset by peer` |
| `curl -k https://...:46795/` | TLS встановлюється, далі `tlsv1 alert internal error` на будь-який HTTP-запит |
| `openssl s_client` | самопідписаний сертифікат, `CN=SRV-Vladiyan`, 17.06.2026 – 17.12.2026 |
| перебір 12 імен публікації по https | усюди `000` — тіла відповіді немає |

## Висновок

На порту `46795` **немає веб-сервера і немає веб-публікації 1С**. Поведінка
(TLS є, HTTP обривається алертом, сертифікат виданий на ім'я комп'ютера)
характерна для **RDP**: до 1С підключаються через віддалений робочий стіл до
Windows-сервера `SRV-Vladiyan`, а не через веб-клієнт.

Отже стандартний інтерфейс OData не «вимкнений» — його поки нема де вмикати.
Питання «чи можна включити OData» замінюється на «чи можна опублікувати базу
на веб-сервері».

## Розвилка

**Якщо Windows-сервер наш** (є права адміністратора):

1. Ставимо/використовуємо IIS на цьому ж сервері, публікуємо базу.
2. Увімкнюємо стандартний інтерфейс OData у публікації, заповнюємо його склад.
3. **n8n ставимо в ту саму мережу** — тоді OData не виставляється в інтернет
   взагалі: обмін ходить по локальній адресі. Зникають питання сертифіката,
   білого списку IP і Basic-авторизації через відкритий інтернет.
4. Варіант A з `PLAN.md` зберігається повністю, ризик №1 закривається.

Це найкращий зі можливих розкладів: простіше і безпечніше за початковий план.

**Якщо сервер чужий** (дали тільки RDP):

1. Заявка власнику: опублікувати базу на веб-сервері + відкрити порт + сертифікат.
2. Якщо відмова — варіант B: регламентне завдання в 1С вигружає товари та
   залишки у файл і **саме** відправляє їх на наш SFTP або HTTP-ендпоінт n8n.
   Вихідне підключення заявки на відкриття портів не потребує, тому цей шлях
   зазвичай проходить там, де вхідний доступ не дають.

## Що перевірити всередині RDP-сесії

```powershell
Get-Service | Where-Object { $_.Name -match 'W3SVC|Apache|1C|srv1c' } | Format-Table Name,Status,DisplayName
Get-ChildItem C:\ -Recurse -Filter default.vrd -ErrorAction SilentlyContinue | Select-Object FullName
netstat -ano | Select-String LISTENING | Select-String ':80 |:443 |:1540|:1541'
Get-ChildItem 'C:\Program Files\1cv8' -Directory | Select-Object Name
```

Перша команда покаже, чи є веб-сервер і служби сервера 1С; друга — чи база вже
кимось опублікована; третя — що слухається; четверта — версію платформи
(склад інтерфейсу OData налаштовується з 8.3.5).

## Побічна знахідка: сертифікат

Самопідписаний, `CN=SRV-Vladiyan` не збігається з доменом, діє до **17.12.2026**.
Якщо публікацію все ж виставлятимемо в інтернет — потрібен нормальний сертифікат
на `vladiyan.extranet.club`, інакше у грудні обмін встане на перевипуску.
При варіанті з n8n у локальній мережі це питання не виникає.

## Наслідки для архітектури

1. **OData можливий, але дорогий по узгодженнях.** Файлову базу публікувати можна,
   модуль розширення вже стоїть і `webinst.exe` зробить публікацію однією командою,
   але потрібен веб-сервер (немає) і права адміністратора (немає), плюс відкритий
   порт і сертифікат для доступу з n8n.
2. **Регламентні завдання 1С у файловому режимі не працюють автономно** — тільки
   поки відкрита клієнтська сесія. Розклад дає планувальник Windows.
3. **Файлова база блокується конкурентно.** Повне читання каталогу варто робити
   поза робочим часом, а не о 08:30.
4. COM-сесія у файловому режимі **займає ліцензію 1С**.

## Переглянуті варіанти

| | Суть | Потрібно | Оцінка |
|---|---|---|---|
| A′ | Apache/IIS + публікація файлової бази + OData | адмін, відкритий порт, сертифікат | +1 д адміну, три узгодження |
| B | Планувальник Windows запускає `1cv8.exe` у пакетному режимі, зовнішня обробка вигружає JSON і віддає його n8n | 1С-програміст на обробку | +2–3 д, тільки вихідні з'єднання |
| C | PowerShell-агент через `V83.COMConnector` читає базу і POST-ить дані на вебхук n8n | одноразовий `regsvr32 comcntr.dll`, якщо не зареєстрований | +1–2 д, без 1С-програміста |

**Рекомендація: C, з B як запасним.** Обидва працюють тільки на вихідних
з'єднаннях: не потрібні ні відкриті порти, ні сертифікат, ні білий список IP.
A′ вимагає адміна, порту і сертифіката — три узгодження замість одного.

2. Розмір `1Cv8.1CD` — впливає на час прогону.
3. Чи можна створювати завдання планувальника правами користувача `v09`.
4. Скільки ліцензій 1С і чи є вільна під сесію обміну.

# Оновлення 2: вибір варіанта (2026-09-17, фінальна розвідка)

## Нові факти

| Перевірка | Результат | Наслідок |
|---|---|---|
| `New-Object -ComObject V83.COMConnector` | `REGDB_E_CLASSNOTREG` | COM не зареєстрований — варіант C вимагає `regsvr32` від адміна |
| `1Cv8.1CD` | **5 959 933 952 байт ≈ 5,55 ГБ** | велика файлова база; маршалінг через COM буде повільним |
| `schtasks /create` правами `v09` | успішно | розклад двічі на добу робиться без адміна |
| `1cv8.exe` | є | пакетний режим доступний |
| Демо-база | `C:\bas\bases\sh_demo` («Швейка Демо») | всі експерименти робимо на ній |

## Рішення: варіант B

Рекомендація змінена з C на **B** (пакетний запуск `1cv8.exe /Execute` із
зовнішньою обробкою) з двох причин:

1. **Продуктивність.** При базі 5,5 ГБ каталог має десятки тисяч позицій.
   `V83.COMConnector` передає кожне поле через межу процесів, тому читання
   такого обсягу займає хвилини-десятки хвилин. Запит, виконаний всередині
   1С, віддає ті самі дані за секунди.
2. **Нуль залежностей від адміна.** `1cv8.exe` встановлений, планувальник
   працює правами користувача, зовнішня обробка — окремий файл, зняття
   конфігурації з підтримки не потрібне. Варіант C впирається у `regsvr32`,
   варіант A′ — у веб-сервер, порт і сертифікат.

## Цільова схема

```
Планувальник Windows (двічі на добу, права користувача v09)
  └─ 1cv8.exe /Execute export.epf        запит всередині 1С, файлова база
        └─ HTTPS POST на вебхук n8n      тільки вихідне з'єднання
              └─ n8n: мапінг, дельта, batch по 50 → Бітрікс24
```

Не потрібні: веб-сервер, публікація бази, OData, відкриті порти, сертифікат,
білий список IP, звернення до хостера.

## Відкрите питання по розкладу

Завдання має відпрацьовувати, коли в RDP-сесію ніхто не увійшов. Якщо сесія
користувача на сервері зазвичай **відключена, але не закрита** — працює як є.
Інакше завдання створюємо з `/ru v09 /rp <пароль>` (запуск без інтерактивного
входу; може вимагати права «Вхід як пакетне завдання»).
